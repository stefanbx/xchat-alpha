Architecture Report Mesh Network Branch: mesh-public-discovery

How the ӾChat mesh works today

A field map of the live network — who is reachable, how they are found, and how the mesh heals itself — and a straight answer to one question: can a git-delivered relay boot up as a self-healing node that points at the right hub and gets announced, out of the box?

SCOPE  relay/ · deploy/ · app/lib/mesh.dart LAYERS  on-chain discovery + reverse tunnel STATUS  as-built, 2026-08-20
Shipped · auto-promote is the default

A fresh install now becomes a self-healing node — or a hub — with zero config. One constraint still governs it: nodes need hubs.

As of this revision the recommendation in §7 is implemented. A node never needed a hub address baked in — with XC_TUNNEL_AUTO=1 it discovers entry hubs on-chain by capability, seeded from the correct bootstrap list — and the "wake up and heal" machinery (respawn supervisor, tunnel-rebuild watchdog, ledger-driven failover) was always inherited by every mode. What changed: install-relay.sh no longer falls through to a Cloudflare quick tunnel. With no flag it auto-promotes — a public IP becomes a hub, anything behind NAT becomes a public, self-healing node — and --update now inherits a running relay's mode instead of re-homing it. The one hard constraint remains, by design: a node is only reachable through a live hub, so the hosted hubs stay the guaranteed floor. Diagrams and the shipped commands below.

§1
The cast

Three roles, one distinction that decides everything

Every participant runs the same relay binary (xc_relayd.py, plus the node /api layer). What a box is comes down to a single runtime fact — does it dial outward through a tunnel? — read lazily at request time:

  • Hub — a relay with a public IP. Reachable directly, and can front NAT'd relays as an entry. Advertises capability t1. relay_type() → 'hub'
  • Node — a relay behind NAT. Cannot accept inbound; reachable only through hubs. It is a tunnel client. relay_type() → 'node'
  • App — the phone. Holds no server; reaches nodes and hubs over HTTPS and reads the Nano ledger to heal its endpoint list.

"Entry" and "hub" are the same box seen from two sides: hub is the app-facing word, entry is the tunnel-code word. A box is a node the instant XC_TUNNEL_ENTRIES or XC_TUNNEL_AUTO is set (it dials out); otherwise it is a hub. A client can never also be an entry — you can't front others while hiding behind them.

§2
Discovery · Layer 1

Finding a public relay: the ledger is the directory

There is no registry server and no DNS to trust. A public relay makes itself findable by writing to the one shared surface everyone can already read — the Nano ledger. Three keyless rendezvous accounts (derived from fixed seeds 0x3A / 0x3B / 0x3C) act as meeting points: plural, so losing one is survivable; ownerless, because the network only ever reads them.

To announce, a relay derives a keypair from its own URL, sends a dust "check-in" to each rendezvous account, then commits its URL as the link field of its latest block — recoverable by any client with a plain block_info RPC and no IPFS. A ledger scan of the rendezvous receivables yields the live relay set. On top of that sits fast HTTP gossip: a signed {url,account,ts,sig} record pushed to bootstraps and a random peer sample, relayable onward because the signature travels with it.

§3
Discovery · Layer 2

Reaching a NAT'd node: a reverse tunnel with no external service

A relay on a laptop can dial out but nothing can dial in. The usual fix is Cloudflare, localhost.run, or Tailscale — an external service and a single point of failure. ӾChat's alternative uses other ӾChat hubs as entries. The node opens outbound long-poll connections to several hubs at once and serves itself through all of them. Kill any one hub and the others carry it.

The transport is nothing but HTTP: a hanging GET /_tunnel/poll waits for work, a POST /_tunnel/reply returns the response. It passes through every ingress untouched, needs no WebSocket, and adds no dependency. One extra round-trip of latency is the whole cost.

§4
Anonymity · Layer A

Why the address is a rotating token, not an account

A hub relays a node's bytes, so it inevitably sees the flows it carries. What it must not learn is whose flows they are. So routing is keyed on an ephemeral token, never the node's ledger account:

This is Layer A: it unlinks a flow from an identity. It does not defeat a single hub correlating "this inbound request ↔ this outbound reply" by timing — that needs ≥2 hops (a mix layer, Layer B), which is a separate, not-yet-built feature.

§5
Reachability

"Announced" means two different things for a node

This is the crux of the original question. A node never announces itself on-chain — its only routable identity would be a loopback address every hub would learn, fail to probe, and tombstone. So "getting a node announced" is not the ledger path from §2. A node has exactly two reachability modes, and the difference is one environment variable:

◆ Private-by-secret default

The node stays invisible. It appears in no directory. Only someone holding the rendezvous secret can derive its token and reach it at <hub>/r/<token>.

The hub never lists it; the account↔hub link is never exposed. Maximum anonymity, zero automatic discovery — you hand the secret out yourself.

XC_MESH_PUBLIC unset · gossip_out() returns early

◆ Public listing --public

Each poll carries a public=1 flag, so every hub adds the node's token to its /mesh_nodes list. Apps sweep that list and reach the node with no secret at all.

This is what "announced" means for a node. The cost, stated in the code: it "trades the node's anonymity — its account↔hub link becomes visible — for zero-config reachability."

XC_MESH_PUBLIC=1 · EntryHub.public_nodes() · GET /mesh_nodes

So a git-default node that is discoverable by every app must ship with XC_MESH_PUBLIC=1 (--public). That is a deliberate privacy trade, not a free win — worth making the default explicit about.

§7
The question, answered — and shipped

Yes — the git default is now a self-healing node (or a hub)

A fresh install-relay.sh used to resolve to MODE=quick — a Cloudflare quick tunnel whose URL changes every restart and cannot be announced. That fallthrough is gone. With no flag the installer now reads what the box can do and picks a role; the pieces people assumed were missing were already present. Status of each requirement, and what actually changed:

RequirementNowHow
Tools to run a node Was already there One curl … | sh installs relay + node + tunnel client. A git operator has the full toolset.
Correct hub address Never needed one XC_TUNNEL_AUTO=1 discovers hubs on-chain by the t1 cap, seeded by the (correct) bootstrap list. Nothing to hard-code per node.
Wake up & heal Was already there Respawn + heartbeat + tunnel watchdog + client failover (§6), inherited by every mode.
Is a node by default Shipped Zero-flag default now auto-promotes: public IP → hub, NAT → mesh node. --quick keeps the old tunnel.
Gets announced Shipped An auto-promoted node sets XC_MESH_PUBLIC=1 (discoverable, no secret). --mesh-tunnel alone opts back to private (§5).

The one hard constraint

A node is reachable only through a hub. If the git default makes everyone a node and nobody runs --hub, there are no entries to dial — every node is invisible and the mesh has no floor to stand on. "Default to node" cannot mean "default to node everywhere." The network needs a guaranteed population of public hubs before a node-heavy default is safe.

What shipped

  1. The default auto-promotes. The zero-flag path now resolves a public IP to a hub and everything else to a public, self-healing node — reusing detect_public_ip() plus a new is_public_ip() that rejects RFC1918, CGNAT, loopback and link-local. --quick was added to still ask for the old Cloudflare tunnel; --mesh-tunnel alone stays private.
  2. Update is safe. Re-running the installer inherits the mode a prior install baked into run.sh — no silent re-homing — which also fixed a latent bug that reverted non-quick installs to quick on every update.
  3. The privacy trade is spoken aloud. The install prints which role it picked and how to override, including that a public node reveals which hub carries it, with --mesh-tunnel as the private opt-out.
  4. Guarded by tests. Two source-level tests extract and run the real shipped shell — the classifier's boundaries, and the resolution across fresh installs and updates.

Still deliberately the operator's own step: setting a payout wallet (default takes no payments) and on-chain announcement of a hub (needs a funded key). And the architectural constraint is unchanged — a node is only as reachable as the hub population is healthy, so the hosted hubs remain the funded floor.
